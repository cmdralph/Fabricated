# Fabricated v0.5.1-alpha

> **Pre-release.** Fabricated is in early alpha and not ready for production. Builds are stable in CI, but many Fabric
> mods still won't run. Use these builds at your own risk, and back up your worlds.

An update to v0.5.0-alpha for packs that mix Fabricated with Sinytra's mods: Forgified Fabric API, Sodium's NeoForge
build, Kotlin for Forge, and NeoForge mods that bundle Fabric API modules.

## Highlights

- **Joining a world works on 1.21.1 again.** Since v0.4.0, the integrated server could crash as a world loaded, with
  "NoClassDefFoundError: com/google/gson/internal/Streams" in vanilla's code reading a player's stats, and OneConfig
  failed reading its settings the same way. Fabricated's loader for the jars mods add to the class path hid part of the
  launcher's libraries (Gson's internals) from the game. Forge 47 had the same fault.
- **Packs with Forgified Fabric API start.** v0.5.0 stopped them before any mod ran, with a `ResolutionException`
  ("Modules fabricated and fabric_screen_handler_api_v1 export package ..."). Now every package has one owner:
  - a Fabric API module another mod provides (Forgified Fabric API's, Sodium's bundled ones) is that mod's, and
    Fabricated's own copy stands down, with its mixins and event bridges;
  - Fabric Loader's API is always Fabricated's: another jar's copy (Forgified Fabric Loader's) is left out;
  - Kotlin is Kotlin for Forge's when it is installed, on every version, as is any library a NeoForge mod bundles.
  The report lists who provides what under *Fabric API modules provided by other mods* and *Fabric Loader API*.
- **Sinytra Connector next to Fabricated is refused with a clear error**, as is a second Fabricated jar: the launch
  stops with one message naming the jars (on 1.21.1 too, where two Fabricated jars would otherwise end in a module
  error). Keep one of them.
- **Fewer Fabric mods disabled for nothing:**
  - Forgified Fabric API's versions (`0.116.15+2.3.6+1.21.1`) and its `fabric` and `fabric-api` ids now satisfy
    Fabric mods' dependencies;
  - a mixin that needs a Fabric mod that isn't loading is left out, and its mod loads without it, where Mixin would
    have stopped the game (OneConfig's chat mixin, which needs adventure-platform-fabric: a client with OneConfig and
    PolyPlus now reaches a world);
  - with Forgified Fabric API, Fabric mods that create their own registries no longer fail their initializer;
  - no more false "missing class" warnings for classes another installed mod has.

## What's fixed on NeoForge

- **Coexistence** (PROVIDER-1 to PROVIDER-4, PROVIDER-6, DUP-2): see Highlights. Forgified Fabric API's resource
  loader no longer stops the server on a Fabric mod's built-in pack that carries its NeoForge build's sections: a Fabric
  mod's files now look to other mods as NeoForge reads them. Forgified Fabric API's registry builder works from Fabric
  initializers, which Fabricated runs after the point NeoForge accepts new registries at (Connector runs them
  earlier).
- **Dependencies** (VER-2, DEP-1): version ranges against build metadata with `+` in it, and mods depending on the old
  `fabric` id.
- **Multi-loader jars** whose NeoForge side is only a placeholder for Connector load as the Fabric mods they are.
- **Translated jars** are named after their mod in NeoForge's logs, not `remapped.jar` (NAME-1), and Fabricated's
  own in-game mod is `fabricated.jar` in a crash report's mod list, not a hash.
- **Libraries the platform already has** (GSON-1, PKG-5): vanilla reads Gson's internals again on 1.21.1 (see
  Highlights). With Kotlin for Forge, Fabric Language Kotlin's copy of Kotlin is now left out on 1.21.11 and 26.x too,
  where it loaded beside Kotlin for Forge's; a Fabric jar's copy of any library a NeoForge mod bundles is left out for
  that mod's.
- **Fabric Loader's `FabricLauncher.loadIntoTarget`**, which OneConfig calls, is provided.
- **1.21.1:** the login listener accessor its shared code expects is applied (MIX-2; Fabricated runs no login queries,
  so nothing hit it).
- **CI:** every version runs a server with stand-ins for Sinytra's mods (a module provided straight and nested, a copy
  of Fabric Loader's API, two versions of a nested library), the real Forgified Fabric API with the test mods where it
  has a build for the version, and a refusal check for Connector and a second Fabricated jar. Every run reads a
  player's stats as vanilla does, beside a test jar bundling part of Gson, and a client joins a world with Kotlin for
  Forge and Fabric Language Kotlin.

## Forge builds (experimental)

The Forge builds remain **experimental previews**: use them for testing, not for playing. They now come from their own
branches only (`forge` for Forge 61, 64, 65 and 66; `forge-legacy` for Forge 47) and get the shared engine's fixes
(version ranges against build metadata with `+` in it, the mixins left out when they need a Fabric mod that isn't
loading, and the class-path fix that lets vanilla read Gson's internals, GSON-2). The provider policy and the
Connector refusal are wired on NeoForge only so far.

## Known limits (NeoForge)

- **With Forgified Fabric API, its modules are used as they are.** What they do differently is theirs: its networking
  refuses a payload in the `minecraft` namespace, so a Fabric mod registering one fails its initializer (PROVIDER-5),
  and on 26.x its item API stops the game when asked the equipment slot of an item that sets one the Fabric way
  (PROVIDER-7).
- **OneConfig** loads, with two differences from Fabric. Its keybind registry can't reach `KeyMapping.MAP`, which
  NeoForge retyped (OneConfig warns that its keybinds may shadow Minecraft's). adventure-platform-fabric is disabled:
  two of its mixins add Adventure's interfaces to library classes NeoForge loads without mixins, so OneConfig's chat
  handling finds `Component.asComponent()` missing. Naming those two mixins in `skipMixins` loads it; its identity and
  command-exception helpers then fail where called.
- **Login queries** (`ServerLoginNetworking`, `ClientLoginNetworking`) aren't supported, because NeoForge has no hook
  for that phase.
- **Renderer mods:** the Fabric builds of Sodium and Iris are refused by default. Use their NeoForge builds.
- **Fabric renderer API on 1.21.1:** Fabric models with their own block quads aren't drawn in chunk sections yet
  (FRAPI-5).
- **Some popular mods still stop 1.21.1:** Moonlight (CORPUS-44), LambDynamicLights on the client (CORPUS-45), Pehkui
  (CORPUS-46).
- **A Fabric mod whose initializer fails** is marked failed and the report says why; if it failed after setting up its
  networking, joining a singleplayer world can wait without end (ENTRY-1).
- **Multiplayer:** CI tests dedicated servers and singleplayer clients, but not a client joining a dedicated server.

## Installing

1. Install NeoForge (or, for testing, Forge) for your exact Minecraft version.
2. Download the jar for that version:
   - NeoForge: `fabricated-0.5.1+mc<minecraft>.jar`.
   - Forge: `fabricated-forge-0.5.1+mc<minecraft>.jar`.
3. Check the jar against `SHA256SUMS.txt`.
4. Put the jar in `mods`, next to your Fabric mods and the official Fabric API jar for that version (or Forgified
   Fabric API, whose modules Fabricated then uses). Remove Sinytra Connector, and any older Fabricated jar.

Fabricated never downloads anything and never modifies your mod jars. `logs/fabric-bridge-report.txt` says what loaded
and why anything didn't.

If you hit a crash, please open an issue and attach `logs/latest.log` and `logs/fabric-bridge-report.txt`.
